PHASE 3 – REDESIGN THE UI (CODE) BASED ON THE NEW DESIGNS
=================================================================

For each screen in `FEATURE_SCREEN_MAP`:

1) Take the existing implementation:
   - Components, pages, routes.
   - Form structures, tables, filters, dialogs.
2) Apply the new UI layout and visual design:
   - Use the structure, layout, spacing, typography, and components from ui_design_28_nov_2025.
   - Implement consistently (e.g., shadcn + tailwind or current design system).
3) Preserve and rewire:
   - All existing business logic hooks.
   - All field bindings (values, validation, error messages).
   - All actions (create, update, delete, transitions).
4) Ensure:
   - No functional regression.
   - New UI does not drop required fields or flows from MASTER_SPEC_IMPLEMENTATION_CHECKLIST.md.

=================================================================
PHASE 4 – DETECT & DOCUMENT ALL DEVIATIONS FROM MASTER SPEC
=================================================================

Create a new document:

- File: docs/UI_SPEC_DEVIATIONS_28_NOV_2025.md

For **each** conflict or deviation where ui_design_28_nov_2025 differs from MASTER_SPEC_IMPLEMENTATION_CHECKLIST.md:

Document a structured entry:

- `Screen / Area:` (e.g., Driver Scheduling, Insurance Claims New, Report X)
- `Checklist Reference:` (ID from MASTER_SPEC_IMPLEMENTATION_CHECKLIST.md)
- `UI Design Behaviour / Element:`
  - What the UI design proposes (field, flow, step, removal, extra chart, etc.)
- `Spec Behaviour / Requirement:`
  - What the checklist/spec actually requires.
- `Deviation Type:` 
  - Missing field / Extra field
  - Changed flow / Additional step
  - Different validation / Different permissions
  - Different aggregation / Different report measure
- `Is this deviation needed?` (YES/NO/MAYBE)
  - Why it might be beneficial (usability, clarity, performance, business need).
- `How can it be implemented?`
  - Changes required to models, APIs, workflows, permissions, or data.
- `What will this break or impact?`
  - Impact on:
    - Existing flows
    - Data integrity
    - Reports
    - Integrations
    - Tests
- `How to mitigate and keep system stable?`
  - Migration steps
  - Backward compatibility considerations
  - Additional validations or feature flags
- `Recommendation:`
  - Implement as new spec change
  - Reject the deviation
  - Park for future version (v1.x / v2)
- `Status:` 
  - ACCEPTED_FOR_FUTURE / REJECTED / UNDER_REVIEW / IMPLEMENTED

RULE:
- No deviation is allowed silently.
- All must be explicitly listed in UI_SPEC_DEVIATIONS_28_NOV_2025.md.

=================================================================

1) Run unit + integration + e2e tests for the relevant module.

3) If any test fails:
   - Fix the UI wiring or logic.
   - Do NOT change spec behaviour to “match the UI”; change UI to match the spec, unless deviation is explicitly documented and accepted.
